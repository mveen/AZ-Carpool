# Push-meldingen (test en live)

Server-based push notifications for **Ritten ruilen**. Two independent switches, both **off by default**:

| Switch | Where | What it does |
|---|---|---|
| **Test aan** (`settings/push.mode = 'test'`) | Beheer → Berichten → *Push-meldingen testen* (coordinator only) | Lets the server send test pushes to the **coordinator's own test devices only**. Works whatever the other switch says, so the coordinator can always test. |
| **Push-meldingen aan** (`settings/push.live = true`) | Beheer → Berichten → card *Ritten ruilen*, under the Ritten-ruilen switch | Lets **parents** switch on real pushes on their own phone (Instellingen → *Push-meldingen*); the server then sends them the notifications of their family. |

**What it is.** A Beheer card *Push-meldingen testen* (Berichten), the push switch on the card *Ritten ruilen*, the row *Push-meldingen* in Instellingen (only visible while the push switch and Ritten ruilen are on, for a browser that belongs to a family) and a server job (`cron/push.mjs`). Test pushes are labelled "Test · Ouder van Saar" (the family they were meant for) and a tap opens the app in *Testweergave* as that family; the card also has a preview, five made-up situations. A real push is the plain notification text and a tap opens Ritten ruilen, scrolled to *Meldingen* (`?open=ritbeurs`).

**Who gets what** (`routeEntry` in `push.js`, used by the server):
- Made-up situations, the button *Stuur naar mijn toestel* (`manual: true` in the queue entry) and, while live is off, copies of real notifications → the coordinator's **test devices** (owner `coordinator`), only while *Test aan* is on.
- A **real** notification → the **devices of the family it is for** (`familyId`), only while live is on, only when the notification was made after live was switched on (`settings/push.liveSince`), and only to phones that were switched on before it was made (no old news after switching on). While live is on the coordinator no longer gets test copies of real notifications.
- Nothing else is ever sent. A family without a phone simply gets no push; the notification itself is still in the app.

**Safety, in layers.**
1. `settings/push` holds `{mode, live, liveSince, updatedAt}`. Only the exact word `test` and only `true` switch anything on; a missing or broken document means both off. With both off the server job does nothing at all and the app writes **nothing extra** for anybody. Both switches are always written together, so changing one never wipes the other.
2. The server only sends to real push-service addresses (Google, Mozilla, Apple, Microsoft). `firestore.rules`: only the coordinator creates a test device; a member creates a phone only for the **own family** and only while live is on; a parent may read, change or remove only the phones of the own family; nobody but the coordinator lists the collection.
3. The test screens are hidden for everybody but the coordinator (`push-access.js`).
4. Made-up situations are stored in `testNotifications/` and never touch `offers`, `backupMoments`, `deviations`, `groups`, `families` or a family's own `notifications` (a test checks this for all five).
5. With a switch on, a real notification (Ritten ruilen must be on) also gets an entry in `pushQueue/`, written *after* the real data and best effort: a failing queue never breaks offering or taking over a ride.

**Data (all additive).** `settings/push {mode, live, liveSince, updatedAt}`; `settings/pushKey {publicKey}` and `settings/pushStatus {lastRunAt, mode, live, sent, failed, pending, devices, familyDevices, announced}` (written by the server only); `pushDevices/{id}` (`owner: 'coordinator'` = test device; `owner: 'family'` + `familyId` = a parent's phone; the coordinator's own phone can be both: it keeps `owner: 'coordinator'` and gets a `familyId`); `pushQueue/{path with / as __}` (+ `sentTo`, `failedTo` by the server); `testNotifications/{id}` (vanish after a day).

**The server job** (`bash ~/azcarpool-cron/run.sh push`). While *Test aan* **or** *Push-meldingen aan* is on: makes the key pair once (`~/azcarpool-secrets/push-vapid.json`, mode 600, never in git or in the database) and publishes the **public** half in `settings/pushKey` (parents read it to subscribe); sends due `pushQueue/` entries as described above (never twice: `sentTo`, and the notification `tag`), removes devices the push service says are gone (404/410), gives up on a device after 5 failures, removes expired entries, and reports itself in `settings/pushStatus` (both cards show "Server actief" or a warning). It also announces **"niet gedekt"** (an offer still open at 18:00 the day before) on the server, so that no longer needs an open app; it uses the same rules as `checkRitbeurs` and *creates* the notifications in one commit with the offer change, so the app and the server can never make it twice. The encryption (RFC 8291) and the signature (VAPID, RFC 8292) are written with Node's own crypto, no libraries; the tests check them against the RFC's worked example. A lock file keeps two runs from overlapping. The content of a message is encrypted end to end (the push services only see that a message was sent, not what it says).
- **Quota (v121):** the job does nothing between 00:00 and 05:00 Amsterdam time (an entry that was due goes out from 05:00), reads `pushQueue` first and only reads `pushDevices` and `families` when there is something in it (the device counts in `settings/pushStatus` are then left out), and only reads `families` and the day coordinators when an offer is really due (*niet gedekt*). An idle run costs about 4 reads plus the offers.
- **Cron:** while testing and in the first days of live, **every minute**: `* * * * *  bash ~/azcarpool-cron/run.sh push > /dev/null`. **Afterwards every 5 minutes:** `*/5 * * * *  bash ~/azcarpool-cron/run.sh push > /dev/null`. Same service account key as the other jobs (`calendar-key.json`, *Cloud Datastore User*). Reads per run with a switch on: about 6 plus one per due entry; with both off: 1.
- **Order of the first run:** (1) paste the new `firestore.rules` into the Firebase console, (2) deploy the app, (3) the cron line is there, (4) Beheer → Berichten → *Push-meldingen testen* → **Test aan** → within a minute "Server actief" appears and the key is published, (5) tap *Meldingen aanzetten op dit toestel* on each test device (Android: Chrome; Mac: Chrome, Edge or Firefox; **iPhone only works with the app on the home screen**), (6) choose a family under *Ik ben…* and play a situation (see `docs/TESTSCRIPT-MELDINGEN.md`), (7) when satisfied: switch **Push-meldingen aan** on the card *Ritten ruilen*, tell the parents to open Instellingen → Push-meldingen on their phone (also in the Help), watch the number of families on the card.
- If `push-vapid.json` is lost the job makes a new pair and publishes it; then each phone must be switched on again.

**Testing it (checklist for real devices).** The automated tests cannot reach the real push services, so this part is by hand: `docs/TESTSCRIPT-MELDINGEN.md` for the test devices. For the live part, with two phones of two different families (or one phone and the coordinator's): switch live on; switch Push-meldingen on in Instellingen on both; offer a ride as one family and check the other family gets the plain push (no "Test ·") and that a tap opens Ritten ruilen at *Meldingen*; check the coordinator's test phone gets **no** extra copy; switch live off and check nothing arrives; remove the phone in Instellingen and check it no longer receives anything.

**The restriction on the test screens.** `push-access.js`: `COORDINATOR_ONLY = true` keeps *Push-meldingen testen* coordinator only (the only line in the app that decides who sees those screens). The parents' own switch (Instellingen) does not depend on it; it depends on the live switch. A test fails if another file starts to know the flag.

**Privacy.** The app stores the push address of a parent's phone (`pushDevices`, with the family) only when that parent switches it on, and removes it when switched off. The push services of Google (Chrome, Android), Mozilla (Firefox) and Apple (Safari on iPhone) only see that a message was sent. The Help (`help-nl.js`: *Push-meldingen op mijn telefoon*, *Over deze app: privacy en AVG*, *gebruikte diensten*) says so.

**`firestore.rules` changed: paste the new rules into the Firebase console → Rules** (blocks `pushDevices`, `pushQueue`). Tests: the unit tests above plus `firebase/rules-test/push-rules.test.mjs` (Firestore emulator, same way as the Ritten-ruilen rules). Service worker cache `az-carpool-v98` (the worker passes `open` of a push to the app).

## Manual smoke test on a phone (before every go-live)
Automated tests cover logic and page output, but not a real phone, real Firebase, or the real WhatsApp app. Check these on a mobile browser:
1. Open the app and log in (parent through the gate, or coordinator).
2. Open Rooster: rides for the week show, no error banner.
3. Open Wijzigen and report a deviation. Save it and see it in Rooster.
4. Press "Deel update via WhatsApp". WhatsApp opens with the message ready. Do not send it if this is only a test.
