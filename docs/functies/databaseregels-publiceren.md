# Databaseregels publiceren (`firebase/firestore.rules`)
`scripts/publish-rules.mjs` compares the file with what is live and publishes it through Google's Firebase Rules API (no libraries). The repo is the truth: what is in `main` is what goes live.
- **In the pipeline:** `deploy.yml` publishes to `az-carpool-test` in the *deploy-test* job (so the robot tries the app and the rules together) and to `az-carpool` in the *deploy-live* job (only after a green robot). Google must accept the rules first; rules that do not compile are never published. The previous rules stay in the Firebase console (Rules -> history) to put back by hand.
- **By hand:** Actions -> *Databaseregels* -> Run workflow: *vergelijken* (changes nothing, shows the lines that differ) or *publiceren*, for *test* or *live*.
- **Keys (once per project, GitHub secrets `RULES_KEY_TEST` and `RULES_KEY_LIVE`):** in the Google Cloud console of that project: IAM & Admin -> Service accounts -> Create service account (name `rules-publisher`) -> role **Firebase Rules Admin** (nothing else) -> open the account -> Keys -> Add key -> JSON. Put the whole content of the downloaded file in the GitHub secret (repo Settings -> Secrets and variables -> Actions) and delete the file. A key only works for its own project: the script refuses a test key for live and the other way round.
- **Rules tests:** `firebase/rules-test/*.test.mjs` run against Google's Firestore emulator with `bash scripts/run-rules-tests.sh` (Java 21 or newer) and in CI in `.github/workflows/rules-tests.yml`, on every pull request that touches `firebase/` (and by hand). They are not part of `npm test`. *Live rules controleren* (`rules-live-check.yml`) compares the published rules with the file every day.
- **Vormcontrole op schrijfacties van leden:** `deviations` (day, direction heen/terug, cars lijst, expiresAt getal), `matchCarpools` (cars lijst), `settings/lastUpdateDeviation` (at getal, by tekst) en `settings/matchCache` (fetchedAt getal, matches lijst). Alleen de types van de kernvelden worden gecontroleerd, geen vaste lijst van velden: nieuwe optionele velden blijven dus mogelijk. Gecontroleerd met `firebase/rules-test/shape-rules.test.mjs` en door alle schrijfacties uit de app-tests (371) tegen de regels af te spelen. Let op: schrijf je in een rules-test een deviation, gebruik dan de echte vorm (zie `ritbeurs-data.js`), niet een afgekort stukje.

## Uitnodigingscodes: minimaal 8 tekens
- Nieuwe codes zijn 10 cijfers. Sinds v275 werkt een code korter dan 8 tekens niet meer voor ouders: de poort in de app weigert hem (`isStrongInviteCode`) en de databaseregels weigeren het opzoeken (`invites/{code}` get) en het aanmaken van een koppeling (`validInviteLink`).
- De coördinator kan een oud, kort codedocument nog wel lezen, aanpassen en verwijderen (opruimen in Beheer).
- Na het mergen moeten de regels opnieuw gepubliceerd worden (plakken in de Firebase-console, of de sleutels `RULES_KEY_TEST`/`RULES_KEY_LIVE` instellen). Tests: `firebase/rules-test/secrets-rules.test.mjs`.

## Wie de coördinator is: alleen voor leden (v278)
- `config/coordinator` bevat een browser-uid of een gezins-id, en een gezins-id bevat de naam van de dochter (`manual-<naam>-…`). Daarom mag alleen een lid het lezen (`allow get: signedIn() && (!exists(coordPath()) || isMember())`). Zolang het document nog niet bestaat mag iedereen kijken: dat is het scherm waar je de coördinatorrol claimt.
- Een bezoeker die nog niet gekoppeld is krijgt `permission-denied` zodra er een coördinator is. De app (`readCoordinator` in `app.js`) leest dat als "er is een coördinator", zonder inhoud. Na het koppelen leest `refreshCoordinatorConfig` het document alsnog, één keer per gezin, zodat een coördinatorgezin direct coördinatorrechten krijgt.
- Volgorde bij het uitrollen: de pipeline publiceert de regels vóór de bestanden van de site. Een nog niet gekoppelde bezoeker met de oude app in de cache ziet daardoor kort "niet verbonden" tot de app ververst. Gekoppelde ouders merken niets. Tests: `firebase/rules-test/coordinator-rules.test.mjs` en de vier tests in `tests/app.test.js` (permission-denied bij het starten, andere fouten blijven fouten, opnieuw lezen na koppelen).

## GitHub Actions vastgezet op commit (v278)
- `actions/checkout`, `actions/setup-node` en `actions/setup-java` staan in alle workflows op de volledige commit-hash, met de versie als commentaar (`# v7`). Een tag kan verschuiven; een hash niet. Dependabot (`.github/dependabot.yml`, wekelijks) werkt hash en commentaar samen bij.

Na het koppelen kan de eerste lezing van `config/coordinator` nog geweigerd worden, omdat de koppeling dan eerst alleen op de telefoon staat en een moment later op de server. `refreshCoordinatorConfig` vraagt het daarom tot drie keer opnieuw (na 1, 3 en 8 s). De smoke test wacht tot 20 s op de Beheer-tab van de coördinator (`beheerTabShown`).
