# De wachtpagina van de host (mijn.host) en de deploy

mijn.host zet voor de hele server een bot-controle voor de website (Imunify360 WebShield). Een robot van GitHub (datacenter-adres) krijgt dan soms minutenlang een wachtpagina ("One moment, please...", een JavaScript-uitdaging) in plaats van de site. De upload zelf (SSH/rsync) heeft er geen last van; de controles en de robottest erna wel. mijn.host zegt dat dit niet per domein of adres uit te zetten is (antwoord van 2026-11-15); de documentatie van Imunify360 kent wel een commando om een domein vrij te geven, dus vragen kan nog.

Wat de pipeline eraan doet, van sterk naar zwak:

- **Fast fallback in the check (`.github/scripts/check-site.sh`):** while the site answers with the wait page, a file is asked twice (`CHECK_WAIT_TRIES`, default 2); then it is read on the host itself over SSH. Once one file had to be read there, the others are asked once. Before, six tries of 10 s per file made this step take about 160 s on a blocked deploy; now about 20 s. A real old version is still asked `CHECK_TRIES` (6) times, because that is the host catching up.

- **Restart after the wait page:** the same bot check can block the GitHub computer that deploys, for minutes: the upload worked but the check afterwards (or the smoke test) gets the wait page. `.github/workflows/deploy-retry.yml` then waits 90 s and restarts the FAILED jobs once (another computer, another address). It only does so when every failed step talks to the host (`scripts/should-retry-deploy.mjs`); a failing test, build or secret check is never restarted, and a second failure stays red. Asking mijn.host to switch the bot check off for `test.azcarpool.nl` would remove the cause, but this works without them.

- **Probe of the host (removed):** a read-only by-hand workflow (`host-probe.yml`) tested on 2026-11-15 whether the wait page can be bypassed from the inside. It showed that an SSH forward returns the real file with the valid certificate, which is what the tunnel below uses. The probe is not needed any more and was removed (2026-11-15); it is in the git history if the host changes its bot check.

- **Robot through a tunnel (optional, needs a one-time setup):** the robot job runs `.github/scripts/open-site-tunnel.sh` before the smoke test: an SSH forward from the GitHub computer's port 443 to the test site's own address, made by the host itself, so the robot's browsers do not meet the wait page (the probe showed the real file with the valid certificate this way). It uses its OWN key, never the deploy key, and never fails the job: without the secret or when the tunnel does not work the log says so and the robot goes straight to the site as before. The log of a run with the key says what the host answered through the tunnel (*REAL FILE* or *WAIT PAGE*). Setup: (1) `ssh-keygen -t ed25519 -f tunnel_key -C az-carpool-robot-tunnel` (no passphrase); (2) on the host add ONE line to `~/.ssh/authorized_keys`: `command="/bin/false",restrict,port-forwarding,permitopen="test.azcarpool.nl:443" ssh-ed25519 AAAA... az-carpool-robot-tunnel` (the key can then only forward to the test site: no login, no commands, no upload); (3) GitHub -> Settings -> Secrets -> Actions -> new secret `TUNNEL_KEY` = the whole content of `tunnel_key`. If the log says the tunnel did not work because the host reaches the wrong site, the host may resolve the name to itself: put the server's public address in `permitopen` and set `TUNNEL_TARGET` to it in the workflow step.

## Een tabblad dat niet opent (smoke test)

Twee keer faalde de robot in WebKit op het tabblad "deviation" (geen wachtpagina: de tunnel stond aan en de rest was groen). `openTab` in `scripts/smoke-test.mjs` klikt daarom na 5 s één keer opnieuw en schrijft dat in het log ("clicking again" / "showed after the second click"), zodat je ziet hoe vaak het gebeurt. Opent het tabblad nog steeds niet, dan noemt de fout de naam van het tabblad en welke tabbladen en knoppen zichtbaar/actief waren. Een echte fout wordt dus niet verstopt, alleen een gemiste klik.
